# `/import` — trazer a configuração do OpenCode para o SelfEvoPI, uma vez

> Estado: **desenho**, não implementado. Passo 2 do agnosticismo.
> Data: 2026-11-19. Worktree: `.worktrees/A11`, branch `agent/A11-agnosticismo`.

## Por que existe

Depois do passo 1, o SelfEvoPI lê a própria configuração:

- MCPs: `~/.pi/settings.json` (chave `mcpServers`)
- skills: `~/.pi/skills/<nome>/SKILL.md`

Quem já tinha 29 MCPs e 334 skills configurados no OpenCode veria `/settings` e
`/skills` vazios. O `/import` traz isso **uma vez**, com consentimento, sem que o
produto volte a ler a config de outro harness em operação normal.

A dependência do OpenCode fica **isolada no caminho de importação** (módulo de
import + `mcp-opencode.mjs`), que é exatamente onde é legítima: importar de outro
produto é um ato explícito do usuário, não leitura silenciosa em todo `/settings`.

## 1. Onde vive

**Comando `/import` na CLI**, com a lógica num módulo `core/agent/import.mjs`.

Justificativa:

- **Precedente `/init`.** O `runInit` (apps/cli.mjs) já faz o formato
  "prévia → confirmação": monta o rascunho, guarda em `pendingInit`, só grava com
  confirmação explícita. O `/import` é a mesma forma — ação destrutiva-ish, exige
  confirmação antes de escrever.
- **Lógica no `core/`, gatilho no `cli.mjs`.** O módulo `core/agent/import.mjs`
  concentra leitura/merge/diff e é coberto pelo gate (`core/agent/*.test.mjs`). O
  `/import` no `cli.mjs` é só gatilho + apresentação. Isso mantém a lógica testável
  e **não toca `cli.mjs` até o passo 4** (quando o `cli.mjs` é liberado).
- **Script não serve sozinho.** Um `scripts/importar.mjs` puro não teria a
  confirmação interativa nem entraria no gate. Cabe como wrapper fino depois, se
  alguém precisar importar em CI, mas não é o caminho primário.

Consequência de fase: o passo 2 entrega o **módulo + teste** (gate verde); a
ligação `/import` no `cli.mjs` acontece no **passo 4**, junto com as renomeações.

## 2. O que copia

### MCPs

Fonte: `~/.config/opencode/opencode.jsonc`, objeto `mcp.servers` (formato rico do
OpenCode: `type`, `command` como array, `environment`, `cwd`, `timeout`,
`disabled`).

Destino: `~/.pi/settings.json`, chave `mcpServers` (formato que o
`mcp.mjs:serversFromConfig` já aceita).

Transformação de cada servidor (a mesma que `normalizeOpencodeServer` faz):

- `command: ["node", "server.mjs", "--x"]` → `command: "node"`, `args: ["server.mjs", "--x"]`
- `environment`, `cwd`, `timeout`, `type`, `disabled` **preservados** no entry
  (o `mcp.mjs` ignora os campos extras ao contar; o probe — passo 1b — usa
  `environment`/`cwd`/`timeout` para abrir o processo).

O scanner de fonte dos MCPs reusa `listOpencodeMcp` (passo 1b), que já devolve o
formato rico normalizado.

### Skills

Fonte: `~/.config/opencode/skills/<nome>/SKILL.md`.
Destino: `~/.pi/skills/<nome>/SKILL.md`.

Cópia de arquivo, lida da fonte e escrita no destino. **Conteúdo copiado verbatim**
(não reescrever o `SKILL.md` do usuário). O frontmatter `name`+`description`
(agentskills.io) é o que o `skills-pc.mjs` já parseia.

> **Consequência de design (do passo 1).** O `listPcSkills` passou a ler o
> **alvo** (`.pi/skills`), não a fonte. O import **não pode reusar `listPcSkills`**
> para varrer o OpenCode. O `import.mjs` precisa do seu próprio scanner da fonte
> (`.config/opencode/skills`), reusando `parseFrontmatter` (exportado) e a mesma
> tolerância a frontmatter quebrado. Isso é bom: isola a leitura do OpenCode no
> módulo de importação, onde é legítima.

## 3. Como não sobrescrever o que já existe

**Merge, não overwrite. "O que já existe vence."**

`s import.mjs` lê o `~/.pi/settings.json` existente (se houver) e, para cada
servidor/skill da fonte:

| caso | ação | relatório |
|:--|:--|:--|
| nome **não** existe no alvo | adiciona | `adicionado` |
| nome **já** existe no alvo | **pula** (mantém o do usuário) | `já existe, mantido` |

Idêntico para skills: se `~/.pi/skills/<nome>/` já existe, pula aquela skill.

Isso torna o import **seguro para rodar duas vezes**: na segunda vez, tudo é
"já existe, mantido", nada é reescrito.

Escrita atômica: escrever em arquivo temporário e renomear, para não deixar
`settings.json` truncado se algo falhar no meio.

## 4. Como é reversível

Duas peças:

1. **Backup do `settings.json`.** Antes de escrever, copiar
   `~/.pi/settings.json` → `~/.pi/settings.json.bak-<timestamp>` (mesmo padrão que
   o `import-providers.mjs` já usa para `models.json`).
2. **Manifesto do que foi criado.** Escrever
   `~/.pi/harness/ledger/import-<timestamp>.json` com:
   - `source`: caminho do `opencode.jsonc` e do dir de skills
   - `backup`: caminho do `.bak`
   - `mcpAdicionados`: lista de nomes
   - `skillsAdicionadas`: lista de nomes
   - `quando`: ISO timestamp

**Rollback** (`/import --undo`):

- Restaura `~/.pi/settings.json` a partir do `.bak` mais recente do manifesto.
- Apaga os diretórios de skill listados em `skillsAdicionadas`.
- Marca o manifesto como `desfeito` (não apaga, para auditoria).

Sem o manifesto, o rollback manual é: restaurar o `.bak` e apagar as skills
listadas — mas o `/import --undo` automatiza.

## 5. O que diz ao usuário

Duas fases, espelhando o `/init`:

**Prévia (default, nada é escrito):**

```
origem: ~/.config/opencode (encontrado)
  MCPs:   29 no OpenCode · 12 já existem em ~/.pi (mantidos) · 17 seriam copiados
  skills: 334 no OpenCode · 40 já existem em ~/.pi/skills (mantidas) · 294 seriam copiadas

nada foi escrito. Responda 'importar' para confirmar, ou outra coisa para cancelar.
```

**Aplicação (após confirmar):**

```
copiados:    17 MCPs, 294 skills
mantidos:    12 MCPs, 40 skills (já existiam)
backup:      ~/.pi/settings.json.bak-2026-11-19T...
manifesto:   ~/.pi/harness/ledger/import-2026-11-19T....json

para desfazer: /import --undo
```

Se a origem não existir: "não achei config do OpenCode em ~/.config/opencode —
nada para importar." (código de saída 0, não é erro do usuário).

## API do módulo (`core/agent/import.mjs`)

```js
// Leitura pura, nada é escrito. Reusa listOpencodeMcp (passo 1b) e um scanner
// próprio para a fonte de skills (.config/opencode/skills).
scanSource({ home })            // -> { configPath, mcpServers: [...], skills: [...] }

// O que já existe no alvo (~/.pi/settings.json + ~/.pi/skills).
scanTarget({ home })            // -> { settingsPath, mcpNomes: Set, skillNomes: Set }

// Diff puro (sem I/O de escrita). Decide adicionar vs manter.
planImport({ home })            // -> { mcpAdd, mcpSkip, skillsAdd, skillsSkip, origemExiste }

// Aplica o plano: backup + merge + manifesto. Atômico no settings.json.
applyImport({ home, plan })     // -> { added, skipped, backup, manifest }

// Reverte o manifesto mais recente.
undoImport({ home })            // -> { restaurado, skillsRemovidas, manifesto }
```

Tudo injetável por `home` (teste usa diretório temporário), mesma disciplina dos
outros módulos de `core/agent/`.
